# 项目终止与复盘

## 1. 什么时候该关闭

- 触达 `CHARTER.md` 里的止损线
- 达到成功线（成功也要正式关闭，否则没人写复盘）
- 连续 30 天没有任何实质动作（僵尸项目）
- 战略转向（先 closeout 旧的，再 init 新的）

## 2. 执行

```bash
journal.py closeout --root <root> --outcome success|failure|pivot|paused --note "判定依据"
```

脚本会自动填入：历时天数、阶段轨迹、条目统计、全部指标、收支合计。**你需要补的是判断，不是数据。**

## 3. 复盘方法（按顺序做，别跳）

### 第一步：重建时间线
读 `INDEX.md` 与各阶段日记，把过程压成 5-8 个关键节点。若某个节点你现在想不起来为什么做，说明当时没记 —— 这是对记录习惯本身的反馈。

### 第二步：找转折点
问三个问题：
- 哪个动作**明显改变了轨迹**？（带来第一批用户 / 第一次收入 / 第一次崩盘）
- 哪个判断**当时看起来对，事后错了**？
- 如果去掉某一个动作，结果会不同吗？

### 第三步：归因（用可检验的写法）
- 写"我做了 X，导致 Y，证据 Z"
- 禁止写"运气不好""不够努力""市场环境"——除非能给出具体证据（比如平台政策变更的公告链接）
- 用**反事实**检验：如果当时做了相反的选项，会更好吗？为什么？

### 第四步：提炼教训（一句话 + 代价 + 边界）
见 `02-writing-guide.md` 的教训范例。每条教训必须能脱离本项目单独成立。

### 第五步：给下一个项目留检查清单
把教训转成**启动时要问的问题**，写进 closeout 第 7 节。下次立项时把这份清单复制进新项目的 `CHARTER.md`。

## 4.  hindsight bias（后见之明）防护

- 引用当时的记录原文，而不是现在的记忆
- 明确标注"当时我以为是 X（有记录为证），实际是 Y"
- 保留错误判断，不要删——它是资产

## 5. 终局档案结构（脚本已生成骨架）

1. 自动事实（脚本填）
2. 关键转折点
3. 成败归因（做对/做错/外部）
4. 可复用打法
5. 不会再做的事（黑名单，附代价）
6. 如果重来一次会怎么改
7. 给下一个项目的检查清单
8. 资产化清单
9. 一句话总结

## 6. 关闭之后

1. `journal.py pipeline` 不存在 —— 跑 `journal.py publish` 生成脱敏资产包
2. 把本项目最有价值的一条教训，用一句话写进你自己的"跨项目经验库"（可用 `vault-index` 汇总）
3. 为新方向 `init` 一个新目录；旧目录永久保留（不要再往里写新内容）

## 7. 常见错误

| 错误 | 后果 |
|---|---|
| 只记成功不记失败 | 学不到东西，资产也没人买（真实才有价值） |
| 复盘写成情绪宣泄 | 不可复用 |
| 用现在的认知改写当时的判断 | 教训失真 |
| 关闭了但不做资产化 | 白干一场 |
| 成功了就不复盘 | 无法复现成功，等于运气 |
