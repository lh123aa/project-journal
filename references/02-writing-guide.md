# 写作指南：什么样的记录才有价值

## 1. 三问测试

任何一条记录，写完自问：

1. **换人可懂吗** —— 三个月后一个不了解背景的 AI 只看这条，能不能理解发生了什么、为什么？
2. **有证据吗** —— 数字、链接、截图路径、报错原文；没有就标 `confidence: low`
3. **可复用吗** —— 下次遇到同类问题，能不能照着做？

三条都不过 = 这是流水账，删掉。

## 2. 事实与判断必须分开

```markdown
事实：10/3-10/8 投放 $120，注册 14 人，付费 0 人，CAC ≈ $8.6
判断：问题不在流量而在定价页——14 人里 9 人停留在价格区块后离开
```

把判断写成事实是最常见的记录污染，会让后续复盘的结论建立在沙子上。

## 3. 好/坏对照

### 决策

**坏**（等于没记）
```markdown
决定用 Telegram 做客服。
```

**好**
```markdown
- 背景：WhatsApp Business API 需要企业认证，我的主体资格不符，等待期 2-4 周
- 选项：
  A. 等认证（成本：2-4 周延误，可能错过投放窗口）
  B. Telegram Bot（零门槛，但东南亚用户渗透率低）
  C. 邮件工单（最通用，但响应慢、转化差）
- 决定：B，先用 Telegram 验证客服流程，认证通过后再迁回 WhatsApp
- 理由：当前瓶颈是"验证是否有人愿意付费"，不是"客服渠道最优"；延误 2 周的机会成本 > 渠道切换成本
- 代价与风险：Telegram 用户覆盖率约 30%，可能导致客服请求漏接；已设置邮件兜底
- 证据：WhatsApp 后台截图 assets/wa-reject-20261003.png
- 下一步：10/15 前统计 Telegram 咨询转化率，决定是否迁回
```

### 问题

**坏**：登录老失败。
**好**：
```markdown
- 症状：登录页提交后 302 回登录页，无报错；复现率 100%
- 影响：阻断全部付费流程，已阻塞 2 小时
- 根因：Cookie SameSite=Lax 导致第三方回调丢失 session（curl -v 观察到 set-cookie 被丢弃）
- 排除过程：先怀疑密码错误（否，日志显示认证通过）→ 怀疑数据库（否，写入正常）→ 抓包定位
- 代价：2 小时 + 一次误判导致的回滚
```

### 教训

**坏**：要早点做用户验证。
**好**：
```markdown
- 一句话：先用落地页收 10 个邮箱，再写第一行代码
- 代价：我在没有需求证据的情况下写了 3 周代码，最终 0 付费，浪费约 90 小时
- 适用边界：适用于需求不确定的新产品；对已有明确客户委托的定制开发不适用
- 复现信号：当我开始说"这个功能做完应该就会有人用"时
```

### 认知（insight）

必须写成"变化"，否则不叫认知更新：
```markdown
- 原来的想法：以为瓶颈是流量不够
- 现在的想法：瓶颈是定价页的说服力——同一批流量换了定价页后转化率 0% → 4.3%
- 依据：A/B 对照，10/3-10/8 vs 10/9-10/14，见 metrics.csv
- 对我的影响：停止加投广告，优先做转化率优化
```

## 4. 量化规则

- 数字必须带**单位 + 时间 + 来源**：`转化率 4.3%（10/9-10/14，GA4）`
- 估算必须标 `估算`，并且写清估算方法
- 不要写"大幅提升""效果好"这类无锚点词；写 `提升 3.1pt（2.2% → 5.3%）`

## 5. 长度控制

- 日记条目：3-8 行，能看懂就停
- 档案：**不超过一屏**（约 40 行）；超过说明里面混了两个主题，拆开
- 大段材料放 `assets/`，正文只写结论 + 指路

## 6. 常见反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 流水账（"今天写了登录页"） | 无人会读 | 只记有判断/有结论的动作 |
| 事后美化 | 学到的是假的教训 | 保留当时的错误判断，写"当时我以为是 X" |
| 只记成功 | 最大的价值丢失 | 失败、放弃、返工必须记 |
| 粘贴整个报错日志 | 噪音 | 贴关键 3 行 + 存全量到 assets/ |
| 结论没有依据 | 无法复用 | 写清证据在哪 |
| 把猜测写成事实 | 污染复盘 | 标注 `判断：` / `估算` |
